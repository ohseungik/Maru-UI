# 접근성 원칙

접근성은 나중에 붙이는 기능이 아니라 컴포넌트를 만드는 방식 자체입니다. 아래 다섯 가지 원칙을 모든 컴포넌트에 같은 순서로 적용합니다.

## 다섯 가지 원칙

1. **네이티브 요소를 먼저 씁니다.** `<button>`, `<input>`, `<select>`, `<dialog>`가 이미 해결해 주는 키보드 조작, 포커스, 폼 연동, 스크린리더 지원을 다시 만들지 않습니다. 직접 구현하는 것은 Tabs나 Tooltip처럼 네이티브 요소가 없는 경우뿐입니다. ([ADR-003](https://github.com/ohseungik/Maru-UI/blob/main/docs/adr/003-build-vs-wrap.md))
2. **키보드만으로 모든 것을 할 수 있어야 합니다.** 마우스로 되는 동작은 키보드로도 됩니다.
3. **포커스가 항상 보여야 합니다.** 키보드 포커스에는 링을 표시하고, 마우스 클릭에는 불필요하게 띄우지 않습니다(`:focus-visible`).
4. **모든 컨트롤에 이름과 설명이 연결되어야 합니다.** 라벨, 도움말, 에러 메시지를 코드로 연결해서 스크린리더가 같은 정보를 읽게 합니다.
5. **사용자의 시스템 설정을 존중합니다.** 다크 모드, 동작 줄이기, 고대비 모드를 따릅니다.

## 키보드 조작

- **Button**: Enter와 Space로 실행합니다. `loading` 중에는 비활성화되어 두 번 실행되지 않고, `aria-busy`가 켜집니다.
- **Checkbox**: Space로 토글합니다. 일부만 선택된 상태(`indeterminate`)를 표현할 수 있습니다.
- **Switch**: `role="switch"`를 가진 체크박스라서 Space로 토글하고 폼에서도 동작합니다.
- **Select**: 네이티브 `<select>`이므로 브라우저와 운영체제의 기본 조작(방향키, 글자 입력 이동)을 그대로 따릅니다. 모바일에서는 기기의 선택 UI가 열립니다.
- **Tabs**: Tab 키는 선택된 탭 하나에만 멈춥니다(roving tabindex). 방향키로 탭 사이를 이동하고, Home과 End로 처음과 끝으로 갑니다. 세로 방향이면 위아래 방향키, 오른쪽에서 왼쪽으로 읽는 언어(RTL)에서는 좌우가 뒤집힙니다. 기본은 이동하면 바로 선택되는 자동 활성화이고, Enter나 Space로 선택하는 수동 활성화도 고를 수 있습니다.
- **Dialog**: 열리면 포커스가 안으로 들어가고, 배경은 조작할 수 없으며, Tab은 대화상자 안에서만 순환합니다. Esc로 닫을 수 있고, 닫으면 포커스가 열었던 버튼으로 돌아갑니다. 이 동작들은 네이티브 `showModal()`이 제공합니다.
- **Tooltip**: 마우스를 올리거나 **키보드로 포커스**하면 열립니다. 마우스 클릭으로 생긴 포커스에는 열지 않습니다. Esc로 닫고, 이때 Esc가 뒤쪽의 Dialog까지 닫지는 않습니다.

## 이름, 설명, 에러

- **Field**는 라벨, 도움말, 에러 메시지를 입력 요소와 `id`로 연결합니다. 입력 요소는 `aria-describedby`로 도움말과 에러를 함께 읽고, 에러가 있으면 `aria-invalid`가 켜집니다.
- 에러 메시지 영역은 `aria-live="polite"`라서, 입력을 고치는 중에 나타난 에러도 스크린리더가 알려 줍니다.
- 필수 표시(`*`)는 장식이므로 스크린리더에서는 숨기고, `required` 속성으로 필수 여부를 전달합니다.
- **Dialog**의 제목이 대화상자의 이름(`aria-labelledby`)이 되고, 설명은 `aria-describedby`로 연결됩니다.
- **Tooltip**은 트리거를 **설명**(`aria-describedby`)할 뿐 이름을 대신하지 않습니다. 아이콘만 있는 버튼에는 `aria-label`이 따로 필요합니다. 툴팁 위로 마우스를 옮겨도 사라지지 않고, Esc로 닫을 수 있습니다. (WCAG 1.4.13)

## 색상과 대비

- 텍스트는 배경 대비 **4.5:1**, 포커스 링과 컨트롤 테두리 같은 비텍스트 요소는 **3:1** 이상(WCAG 2.2 AA)이어야 합니다.
- 대비율은 토큰 테스트가 **라이트와 다크 양쪽**에서 계산합니다. 토큰 값을 바꿔서 기준에 못 미치면 테스트가 실패합니다.
- 색만으로 상태를 전달하지 않습니다. 에러는 문구로, 선택 상태는 모양으로도 표시합니다.

## 시스템 설정

- **고대비 모드**(`forced-colors`): 색에 의존한 표시가 사라지는 환경을 위해 포커스 링, 테두리, 체크 표시를 시스템 색상으로 다시 정의했습니다.
- **동작 줄이기**(`prefers-reduced-motion`): 켜져 있으면 전환과 애니메이션을 끕니다.
- **다크 모드**: OS 설정을 따르고, `data-theme`로 고정할 수 있습니다.

## 어떻게 검증하나

1. **ESLint `jsx-a11y`**: 코드를 쓰는 시점에 라벨 누락, 잘못된 role 같은 문제를 잡습니다.
2. **컴포넌트 테스트**: Vitest와 Testing Library로 실제 키보드 입력(`user-event`)을 보내 동작을 확인하고, `axe-core`로 위반이 없는지 검사합니다.
3. **토큰 테스트**: 라이트와 다크의 색상 대비율을 계산합니다. jsdom은 색을 계산하지 못하므로 컴포넌트 테스트가 아니라 이 단계에서 보장합니다.
4. **Storybook Accessibility 패널**: 스토리마다 axe 결과를 바로 볼 수 있습니다.
5. **시각 회귀 테스트**: 포커스 링이 잘리지 않는지, 고대비 모드에서 형태가 유지되는지를 스크린샷으로 비교합니다.

## 알려진 한계

솔직하게 적어 둡니다.

- 자동 검사는 접근성 문제의 일부만 찾아냅니다. 읽는 순서가 자연스러운지, 문구가 이해하기 쉬운지는 사람이 확인해야 합니다.
- **스크린리더(VoiceOver, NVDA 등)로 직접 확인하는 수동 테스트는 아직 체계적으로 하지 못했습니다.** 계획 중이며, 결과는 이 문서에 기록하겠습니다.
- 대비율은 토큰 조합 기준으로 검증합니다. 사용하는 쪽에서 임의의 색 위에 컴포넌트를 올리면 보장되지 않습니다.

## 사용하는 쪽에서 챙길 것

컴포넌트가 대신해 줄 수 없는 부분입니다.

- `Field` 없이 `Input`, `Select`를 쓸 때는 `aria-label` 또는 `aria-labelledby`로 이름을 붙입니다.
- 아이콘만 있는 버튼에는 `aria-label`을 붙입니다.
- 라벨 없는 `Checkbox`, `Switch`에도 같은 방식으로 이름을 붙입니다.
- Tooltip에는 **없어도 되는 보조 설명**만 넣습니다. 꼭 알아야 하는 정보는 화면에 직접 보여 주세요. 터치 기기에는 hover가 없습니다.
- 에러 메시지는 무엇이 문제이고 어떻게 고치는지를 문장으로 적습니다.
