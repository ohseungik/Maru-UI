# ADR-001: 토큰을 Palette / Scale / Semantic 3단으로 나눈다

- 상태: 채택됨
- 날짜: 2026-10-29

## 배경

디자인 토큰을 "색상 값 목록" 하나로 두면 다크모드와 테마 확장에서 곧바로 문제가 생깁니다.
컴포넌트가 `blue-600` 같은 원시 값을 직접 참조하면, 테마를 바꿀 때 모든 컴포넌트를 고쳐야 합니다.
반대로 모든 값을 의미 이름(`action-bg`)으로만 정의하면, 어떤 값들이 실제로 존재하는지 한눈에 보기 어렵습니다.

## 결정

토큰을 세 계층으로 나누고, 컴포넌트는 가장 윗 계층만 참조합니다.

| 계층     | 예시                                    | 역할                                     |
| -------- | --------------------------------------- | ---------------------------------------- |
| Palette  | `--maru-palette-blue-600`               | 날 것의 값. 색상 팔레트                  |
| Scale    | `--maru-space-4`, `--maru-font-size-md` | 간격, 반경, 타이포, 모션 스케일          |
| Semantic | `--maru-color-action-bg`                | 값에 목적을 부여. **테마는 여기서 교체** |

- 원본은 `packages/tokens/src/tokens.json` 하나이고, 빌드 스크립트가 CSS 변수와 타입이 있는 JS 값을 생성합니다.
- Semantic 값은 `{palette.blue.600}` 형태의 참조로 정의하며, CSS에서는 `var(--maru-palette-blue-600)`로 출력해 DevTools에서 참조 사슬이 보이게 합니다.
- 라이트 테마는 `:root`, 다크 테마는 `[data-theme='dark']`와 `prefers-color-scheme: dark`(명시적으로 `data-theme='light'`를 지정하지 않은 경우)로 제공합니다.
- 컴포넌트 전용 값은 토큰 파일에 두지 않고, 각 컴포넌트 CSS 안의 지역 변수(`--button-bg` 등)로 둡니다. 토큰 수가 컴포넌트 수에 비례해 늘어나는 것을 막기 위해서입니다.

## 검토한 대안

- **Style Dictionary 등 외부 도구**: 기능은 풍부하지만, 현재 필요한 변환(JSON → CSS 변수, JS 값)에 비해 설정과 의존성이 큽니다. 스크립트가 대비율 계산을 포함해 200줄 이내라 직접 구현했고, 요구가 커지면 교체할 수 있습니다.
- **컴포넌트 토큰 계층을 별도로 두기**: 규모가 큰 시스템에서는 유효하지만, 컴포넌트가 몇 개 안 되는 지금은 이중 관리 비용이 더 큽니다.
- **JS 객체(CSS-in-JS 테마)로만 제공**: 런타임 비용이 생기고 SSR 시 테마 깜빡임을 따로 다뤄야 합니다.

## 결과

- 테마 추가는 Semantic 계층에 블록 하나를 더하는 작업입니다.
- 접근성을 토큰 단계에서 검증할 수 있습니다. 텍스트로 쓰이는 전경/배경 쌍은 4.5:1, 포커스 링과 컨트롤 테두리는 3:1 이상이어야 하며, 라이트와 다크 모두 `packages/tokens/test`에서 테스트합니다.
- 라이트와 다크가 정확히 같은 토큰 집합을 정의하는지도 테스트로 보장합니다.
- 단점: 토큰 이름을 바꾸면 소비하는 쪽의 CSS도 깨지므로, 이름은 공개 API로 취급해 semver를 따릅니다.
