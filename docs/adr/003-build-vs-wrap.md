# ADR-003: 직접 구현할지, headless 라이브러리를 감쌀지 정하는 기준

- 상태: 채택됨
- 날짜: 2026-11-11

## 배경

접근성이 필요한 컴포넌트(Dialog, Tabs, Select 등)는 직접 만들 수도 있고, Radix, React Aria 같은 headless 라이브러리를 감쌀 수도 있습니다.
모든 것을 직접 만들면 엣지 케이스에서 틀리기 쉽고, 모든 것을 감싸면 이 프로젝트가 무엇을 설계했는지 보이지 않게 됩니다.
그래서 컴포넌트마다 감으로 정하지 않고, 같은 순서로 따져 보는 기준을 둡니다.

## 결정

컴포넌트마다 아래 질문을 **위에서부터** 던지고, 처음 "예"가 나오는 곳에서 멈춥니다.

1. **네이티브 요소가 이미 해결해 주는가?** → 그 요소 위에 만듭니다.
   `<button>`, `<input>`, `<input type="checkbox">`, `<select>`, `<dialog>`가 해당합니다.
   포커스 트랩, 배경 비활성(inert), Esc, 포커스 복원, 모바일 선택 UI, 스크린리더 호환을 브라우저가 이미 맞게 처리하므로, 이 프로젝트는 시각과 제어형 API만 더합니다.
2. **WAI-ARIA 패턴이 작고 명세가 분명한가?** → 직접 구현합니다.
   Tabs(roving tabindex, 방향키, Home/End)와 Switch가 해당합니다. 패턴을 코드로 보여 주는 것 자체가 이 프로젝트의 목적이기도 합니다.
3. **최신 플랫폼 기능과 단순한 계산으로 충분한가?** → 직접 구현합니다.
   Tooltip은 Popover API(top layer)로 잘림과 z-index 문제를 없애고, 위치는 "뒤집기 + 뷰포트 안으로 밀기"만 하는 순수 함수(`computePosition`)로 해결합니다.
4. **그 외** (충돌 감지, 가상 기준점, 목록 탐색과 타입어헤드, 중첩 레이어 관리가 필요한가?) → headless 라이브러리를 감쌉니다.
   Popover(화살표, 스크롤 컨테이너 충돌), Combobox, Menu, DatePicker가 해당합니다.

감쌀 때의 규칙:

- 라이브러리의 스타일은 쓰지 않고, **스타일은 ADR-002 방식**(CSS Modules + `data-*`)으로 직접 입힙니다.
- 라이브러리 타입을 공개 API에 그대로 노출하지 않습니다. 나중에 바꿔도 소비자 코드가 깨지지 않게 하기 위해서입니다.
- 후보를 고를 때는 접근성 실적, 번들 크기, SSR 동작, 스타일링 방식(unstyled, `data-*` 속성 제공), 라이선스와 유지보수 상태를 비교하고, 그 결과를 이 ADR을 가리키는 새 ADR로 남깁니다. 후보는 Radix Primitives, React Aria, Base UI, Ark UI입니다. 아직 비교하지 않았습니다.

## 검토한 대안

- **전부 직접 구현**: 학습과 설계 의도를 보여 주기에는 좋지만, 위치 계산과 목록 탐색 같은 영역은 사용자 환경이 다양해서(스크롤 컨테이너, RTL, 모바일 키보드) 혼자 검증하기 어렵습니다.
- **전부 headless 래핑**: 가장 빠르고 안전하지만, 소비자에게는 "스타일만 입힌 래퍼"가 되고 이 프로젝트의 가치가 줄어듭니다.
- **기준 없이 필요할 때마다 결정**: 컴포넌트 사이에 접근성 수준과 API가 들쭉날쭉해집니다.

## 결과

- Dialog는 네이티브 `<dialog>` 위에, Select는 네이티브 `<select>` 위에 만들었습니다. 코드가 짧고, 브라우저가 고치는 버그를 그대로 얻습니다.
- 개별 구현 때문에 생긴 문제는 실제로 있었습니다. `<dialog>`는 React가 DOM을 먼저 지우면 포커스를 복원하지 않아 직접 복원 코드를 넣었고, 숨겨진 `<option>`은 접근성 이름이 비어서 placeholder를 이름이 아니라 텍스트로 찾아야 했습니다. 네이티브 위에 만들어도 경계에서 확인할 것이 남습니다. 그래서 컴포넌트마다 실제 브라우저에서 동작을 확인합니다.
- 단점 1: 네이티브 `<select>`는 열린 목록의 모양을 CSS로 거의 바꿀 수 없습니다. 검색, 다중 선택, 항목 안의 아이콘이 필요하면 Combobox를 감싸서 새로 만들어야 합니다.
- 단점 2: Tooltip의 위치 계산은 `transform`된 조상, 매우 작은 뷰포트, 가상 기준점을 다루지 않습니다. 이런 문제가 반복해서 나타나면 이 ADR의 4번으로 옮기거나, CSS Anchor Positioning이 충분히 보급된 뒤 그쪽으로 바꾸는 것을 검토합니다.
